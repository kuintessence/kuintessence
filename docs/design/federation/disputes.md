# 争议、授权披露与仲裁

本文件落实[完整蓝图](blueprint.md#9-慈善资源置换收费与争议)中的 L03/L09，不缩减交付范围，区分目标设计与已实现的共享协议。付款、结算和调整已存在，本文的案件、披露和裁决生产入口尚未接通，不能据此宣称已经具备仲裁能力。

共享字段投影与[双签政策校验](#双签政策与当前授权校验)已实现。它们不单独提供人员审批、持久撤权、远程传输或 PDC 隔离；生产入口仍待接线。

## 授权与私有边界

合作双方 A/B 可自行解决争议，也可事先共同指定仲裁机构 R。无仲裁约定或必要证据未获授权时，案件保持争议；联盟管理员不能替代双方批准、读取商业原件或直接改余额。

| 对象 | 读取范围 | 写入授权 |
| --- | --- | --- |
| 原合同、价格、用量、账单、余额 | 原 A/B 商业集合 | 保持既有 A/B 业务签署和原生背书要求 |
| 案件及指定披露字段 | 新的 A/B/R 案件集合 | 案件政策、披露授权分别核验；不复制完整商业原件 |
| 裁决 | 同一案件集合 | 指定 R 的业务签名及约定的接受条件；集合原生背书按政策配置 |
| 裁决执行记录及账务 | A/B 商业集合 | 核对预授权、裁决、原账目和唯一执行编号后，按原商业集合背书执行 |

不得把 R 加进原商业集合，再用页面过滤隐藏字段。新集合使用 `memberOnlyRead/memberOnlyWrite` 和独立 lifecycle 配置；旧集合成员与历史数据不扩散。公共参数仅包含随机编号，商业正文、完整签名和披露内容放在 transient/PDC；公开集合成员及交易时序仍可能透露合作关系，不承诺组织关系完全匿名。

案件集合可选择 `AND(A.peer,B.peer,R.peer)` 或 `OutOf(2,A.peer,B.peer,R.peer)`。这只是 Fabric 原生背书策略，不能替代业务签署规则：A/B 可以共同和解，但不能冒充 R 出具仲裁裁决；普通管理员证书也不具有裁决权。接受二取三策略意味着接受任意两家串通的风险。

R 不读取 A/B 私有账目，因此不能为依赖这些账目的交易提供同等仿真背书。裁决有效与裁决已记账必须分开：执行裁决仍需要原商业集合的背书。B 的应用拒绝追加人工批准时，可使用事先明确授予的仲裁执行权；B 的 Peer 离线或拒绝背书时，链协调账务仍须等待，不能为了可用性把余额披露给 R 或降级为本地改账。

## 不可变业务对象

沿用原协议的 UUID、带盐 SHA-256、精确整数字符串、原始 JWS 与追加历史，不引入第二套钱包或通用治理引擎。

- **仲裁授权**：A/B 双签，绑定原合作域、合同版本与摘要、A/B/R、有效期、可受理对象、披露字段上限、必要证据、裁决方式、单位及金额上限。配置变更创建新版本；不能对已发生的争议追认原先不存在的扣款权限。
- **案件**：任一有权当事方签署，绑定原任务/attempt、争议对象类型和 ID/摘要、所依据的授权版本、理由与请求。原对象包括用量、账单、结算、调整和付款；只保存对应引用，不能把整个原合同附在发给 R 的开案消息里。
- **披露授权与材料**：A/B 批准案件、接收机构、原件引用、精确字段清单、投影值与有效期限。再次披露新增记录；不修改已披露正文。不以“拥有案件 ID”作为下载授权。
- **裁决**：指定 R 签署，绑定案件版本、授权版本、实际收到的证据摘要与当前账目承诺；记录理由、结果、拟执行动作与金额。和解使用独立 A/B 双签记录，不能伪造 R 签署。
- **执行回执**：绑定裁决、原结算及当前调整 head；只执行一次。保留执行前后金额、执行依据和原交易编号。外部银行付款与退款继续使用独立凭证，裁决不代表银行已经转账。

机构能力分别为开案、披露批准、和解批准、仲裁裁决；密钥用途同样分开显式授予。查看案件不等于可查看原合同，通用平台角色不自动获得这些能力。自动处理只能使用明确的机构政策，不能让当前账单/结算预授权隐含批准仲裁或披露。

## 字段披露

使用按原件类型定义的固定字段白名单，不接受任意 JSONPath、对象扩展或用户传入的已脱敏对象。发送方从已验证的原记录构造投影，复核授权字段和摘要，独立签署新投影；接收方按同一严格 schema 拒绝额外字段。每个字段组的范围必须在批准界面完整可见，例如“账单总额”不能隐含发送各项费率。

投影不得携带原商业 JWS；JWS 可直接解码出未授权字段。R 验证的是双方对所披露事实的签署，不应宣称独立验证了没有收到的原文。仅有原件摘要也不证明该投影与原件相符；双方未确认必要投影时，案件继续等待证据，不能由单方报告完成裁决。技术鉴定材料可单独签署，但不得把它误标为双方确认的事实。

披露前再次检查当前授权、机构状态、密钥用途与案件版本。撤权阻止后续读取和新披露，但无法收回 R 已取得的明文或清除其他成员的备份。不得在界面承诺远端遗忘；保留/删除规则要结合案件 legal hold 和私有集合策略处理。

### 当前字段协议

`@kuintessence/shared/federation/disclosure` 提供 `CommercialDisclosureGrantSchema`、`CommercialDisclosureSchema` 和纯函数 `projectCommercialEvidence`。授权选择绑定案件、政策 ID/摘要、原合作域/版本、A/B/R、原记录 ID/摘要与有效期。接收机构必须与 A/B 不同；空字段、重复字段、通配符、任意路径、额外属性和错误原件类型均拒绝。

| 原件 | 可单独选择的字段 |
| --- | --- |
| 合同 | `consideration`、`unit`、`prices`、`termsText` |
| 用量 | `periodStart`、`periodEnd`、`measurements` |
| 账单 | `grossAmount`、`capReduction`、`discountAmount`、`dueAmount`、`lines` |
| 结算 | `unit`、`reservedAmount`、`chargedAmount`、`releasedAmount` |
| 调整 | `unit`、`previousChargedAmount`、`chargedAmount`、`reason`、`supportingEvidenceDigest` |
| 付款 | `unit`、`amount`、`occurredAt`、`evidenceDigest`、`reason` |

`prices`、`measurements`、`lines` 是显式的完整数组字段组，批准其中一组即披露该组内已定义的全部成员；不能把它们作为“总额”的隐含附带内容。嵌套组也使用严格原字段 schema，额外原文/签名属性拒绝。金额保持整数字符串，零额和明确的 null 不替换或推算。仅批准金额不自动带出单位；后续案件政策必须判断缺单位的证据是否足够裁决。

函数从原始类型校验后的数据提取选定字段，核对原记录、合同、机构、接收方、摘要和有效期，输出与原件脱离的确定性副本，不重新计算原 JWS 字节摘要。它的调用前提是调用方已经验证原件签名以及披露政策和批准；传入一个合法格式的 grant 或 digest 不能代替授权。接收方也必须核验签名和当前政策，不能仅调用响应 schema 就展示材料。独立签署用途和共享双签校验见下文，案件批准、撤权持久化、重放保护和私有集合的生产接线仍待完成。

8 项模块测试覆盖六类投影、大整数、总额/费率分离、确定性与原件不变、错误绑定、时间边界、额外/缺失/跨类型字段、嵌套泄漏与不含私有输入的错误。它们不等于真实三机构披露或 L09 已通过。

### 双签政策与当前授权校验

`@kuintessence/shared/federation/disclosure-authorization` 增加只授予读取范围的 `commercial-disclosure-policy`。双方分别签署同一政策正文，绑定原合同 ID/摘要、合作域、A/B、指定接收机构、允许的原件类型/字段、期限与随机盐。政策不授予仲裁、结算、扣款、外部转账或人员操作权限；额外资金动作字段被严格拒绝。仲裁执行权仍须另外预先约定，不能从披露政策推导。

每份 `commercial-disclosure` 将具体 grantId、案件/政策/原件引用、字段选择与实际投影值一起双签。没有独立的“签了 grant 就允许替换任意投影值”用途。接收侧同时验证政策和披露正文的四个 JWS，按当前信任中机构＋kid 查找唯一密钥，核对用途、有效期、撤销状态以及双方原始签名字节摘要相同。R 签名不能代替 A/B 业务批准；两边各签不同的合法正文也不算双签。

`verifyCommercialDisclosure` 的 context 必须由本地可信案件/原件记录加载，包含 grantId、caseId、policyId/摘要、合作域、合同版本/摘要、A/B/R 和原件类型/ID/摘要。`policyRevoked` 与 `grantRevoked` 都必须明确为 false；不可使用请求体中的未撤销声明。授权字段必须是双签政策的子集，授权期限不能超出政策，且当前时间必须处于授权窗口。接收方不能拿其他 grant 的未撤销状态验证本条披露。

签署用途分别新增 `commercial-disclosure-policy` 和 `commercial-disclosure`，已有密钥不自动扩权；完整用途目录上限同步为 51。Web 信任设置沿用明确勾选并补齐中英文名称，先前遗漏的付款签名用途名称也已补齐。数据库仅扩展既有 JSON 密钥用途的 TypeScript 类型，没有新增 SQL 结构或迁移。

发送前可以用 `assertCommercialDisclosurePolicy` 核对已验证的政策与待签投影范围；它不替调用方检查人员能力、政策/授权的当前持久状态或原件签名。读取状态与发布之间的竞态、机构状态、双方独立人员批准、原始材料真实性、重放存储和传输身份，仍必须在后续生产事务/传输入口中核验。共享验证返回的双签投影不是 R 对未披露原文的独立证明。

9 项真实 RS256 模块测试覆盖政策和正文双签、错误签署机构、同编号异文、字段/期限越界、可信上下文绑定、逐条撤销、密钥用途与有效期、重复 kid、篡改及严格政策格式；原投影和用途目录相关测试继续通过。信任配置的 11 项组件检查通过，不代表正式登录或真实三机构 PDC 验收。

## 冻结与状态转换

案件状态与账务执行、证据交付、链提交状态分别保存，避免一个“已完成”掩盖仍待执行的裁决。

| 状态 | 条件与允许操作 |
| --- | --- |
| `FREEZE_PENDING` | 本站已持久开案并停止新的受影响财务批准，等待对端确认及已签在途事务结果 |
| `DISPUTED` | 双方确认冻结边界，原记录和当前 head 固定；可补材料、和解或申请仲裁 |
| `EVIDENCE_WAITING` | 缺指定机构、必要披露授权或材料；继续冻结，不按超时自动判任何一方胜诉 |
| `DECIDED` | 满足授权及证据条件，裁决/和解原件已验证；仍未必记账 |
| `APPLICATION_WAITING` | 等待原账务依赖、必要背书或原交易 VALID；不另发新裁决绕过等待 |
| `RESOLVED` | 无资金动作的有效结案，或原执行回执已确认；保留全部原件与历史 |

冻结按任务和相关财务 head 定位，不冻结无关合作域余额，也不把科研执行自动取消。执行取消、数据撤权和停止证明继续使用原协议。付款作为已经发生的外部事实可以追加记录；若争议针对付款，新增更正必须纳入案件版本核对，不能借付款凭证修改合作额度。

原始观测、用量报告及技术更正继续追加保留，不因开案而丢弃新证据。冻结阻止受影响的新财务承诺和资金动作；新增事实使待裁决的证据/head 版本过时时，必须重新核对，不能沿用旧版本自动结案。

开案与自动账单/结算/调整存在竞争。Server 必须在原事务锁边界内检查案件；链码的每个相关写入读取同一案件/head，使并发修改触发 MVCC。已双签或已背书的事务不能靠删除队列撤销：先解析原结果，再冻结确定的最新 head；不确定则保持 `FREEZE_PENDING` 并保留占额。跨站点分区期间只能保证本站停止新批准，不能把未收到对端确认显示为全局已冻结。

## 三种模式的执行

| 模式 | 案件与裁决执行 |
| --- | --- |
| 双边直接 | 通过受限 mTLS 交换原件和签名；本地事务执行已授权决定，不需要链 |
| 异步存证 | 与直接模式相同地完成业务，同事务保留私有存证待办；链不可达不阻塞已授权处理 |
| 链上协调 | 案件/裁决保存到独立私有集合，账务按原私有额度与唯一执行记录执行；本站投影等 VALID 后应用 |

链上协调的裁决执行使用窄入口校验原双方仲裁授权、指定 R 签名、证据完整性、结果范围和当前 head，不能复用管理员“直接设置余额”。共享既有金额守恒与占额规则；增额不足时继续等待，不能出现负可用额度。没有仲裁预授权时，只能走双方新签和解及原结算/调整入口。原价、用量与原账单保持不变，更正由追加记录表达。

不自动发行或转移联盟积分，不从直接/异步账本复制余额到链上；原合作域/epoch/单位不能更换。重复裁决、重复投递和重放使用原业务编号与检查点恢复；未确认写入先核对原结果。

## 实现落点与验收

共享协议新增争议对象、严格字段投影和签署用途；链码新增独立案件集合及业务入口，商业链码增加冻结检查与窄裁决执行入口。Server 复用现有独立能力、事务审计、签名交换、outbox 和 Adapter 恢复，不把仲裁流程塞进付款服务。数据库约束通过 Drizzle 生成。Web/CLI 从原任务或财务记录带筛选进入案件，R 使用只含获批材料的案件入口，不复用有完整合同权限的页面。

现有 `FabricEvidenceTrustSchema.domains.siteIds` 是两机构元组，继续用于原 A/B 域；仲裁域另存案件集合与 A/B/R 的明确映射，不把该元组整体放宽成任意成员数组。案件裁决进入 A/B 私有记账时核验案件集合的原记录；从客户端传入“已裁决”状态或裁剪后的回执不能替代原记录和签名检查。

必须覆盖以下真实验证后才能把 L03/L09 标记完成：

1. A/B 能查看原商业内容，R 在自身 Peer/私有存储中仅得到批准的投影，其他机构没有任何案件正文；公开区块、日志和错误不含探针原文。
2. 缺必要证据、错误机构、过期/撤销授权、错误密钥用途、额外字段或携带原 JWS 均拒绝；无授权保持争议，治理身份不能读原件或改账。
3. 正常和解、指定仲裁、冻结与结算竞争、重复执行、过时 head、额度不足，以及 R 无法替 AB 背书的等待路径。
4. 直接/异步处理不依赖链；链协调未经 VALID 不改变本站账目；断链、进程崩溃与原交易恢复不重复扣额或释放。
5. 正式机构身份的 Web/CLI 私有访问与机构切换检查；保留策略不清理活跃争议或执行未确认的原证据。

案件基础协议、PDC 验证、平台接线和用户验收是同一完整交付的必要部分；任何单项通过都不表示仲裁已交付。
