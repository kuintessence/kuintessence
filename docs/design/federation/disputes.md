## 授权与私有边界

合作双方 A/B 可自行解决争议，也可事先共同指定仲裁机构 R。无仲裁约定或必要证据未获授权时，案件保持争议；联盟管理员不能替代双方批准、读取商业原件或直接改余额。

| 对象 | 读取范围 | 写入授权 |
| --- | --- | --- |
| 原合同、价格、用量、账单、余额 | 原 A/B 商业集合 | 保持既有 A/B 业务签署和原生背书要求 |
| 案件及指定披露字段 | 新的 A/B/R 案件集合 | 案件政策、披露授权分别核验；不复制完整商业原件 |
| 裁决 | 同一案件集合 | 指定 R 的业务签名及约定的接受条件；集合原生背书按政策配置 |
| 裁决执行记录及账务 | A/B 商业集合 | 核对预授权、裁决、原账目和唯一执行编号后，按原商业集合背书执行 |

不得把 R 加进原商业集合，再用页面过滤隐藏字段。新集合使用 `memberOnlyRead/memberOnlyWrite` 和独立 lifecycle 配置；旧集合成员与历史数据不扩散。公共参数仅包含随机编号，商业正文、完整签名和披露内容放在 transient/PDC；公开集合成员及交易时序仍可能透露合作关系，不承诺组织关系完全匿名。

案件集合可选择 `AND(A.peer,B.peer,R.peer)` 或 `OutOf(2,A.peer,B.peer,R.peer)`。这只是 Fabric 原生背书策略，不能替代业务签署规则：A/B 可以共同和解，但不能冒充 R 出具仲裁裁决；普通管理员证书也不具有裁决权。接受二取三策略意味着接受任意两家串通的风险。

R 不读取 A/B 私有账目，因此不能为依赖这些账目的交易提供同等仿真背书。裁决有效与裁决已记账必须分开：执行裁决仍需要原商业集合的背书。B 的应用拒绝追加人工批准时，可使用事先明确授予的仲裁执行权；B 的 Peer 离线或拒绝背书时，链协调账务仍须等待，不能为了可用性把余额披露给 R 或降级为本地改账。

## 不可变业务对象

沿用原协议的 UUID、带盐 SHA-256、精确整数字符串、原始 JWS 与追加历史，不引入第二套钱包或通用治理引擎。

- **仲裁授权**：A/B 双签，绑定原合作域、合同版本与摘要、A/B/R、有效期、可受理对象、披露字段上限、必要证据、裁决方式、单位及金额上限。配置变更创建新版本；不能对已发生的争议追认原先不存在的扣款权限。
- **案件**：任一有权当事方签署，绑定原任务/attempt、争议对象类型和 ID/摘要、所依据的授权版本、理由与请求。原对象包括用量、账单、结算、调整和付款；只保存对应引用，不能把整个原合同附在发给 R 的开案消息里。
- **披露授权与材料**：A/B 批准案件、接收机构、原件引用、精确字段清单、投影值与有效期限。再次披露新增记录；不修改已披露正文。不以“拥有案件 ID”作为下载授权。
- **裁决**：指定 R 签署，绑定案件版本、授权版本、实际收到的证据摘要与当前账目承诺；记录理由、结果、拟执行动作与金额。和解使用独立 A/B 双签记录，不能伪造 R 签署。
- **执行回执**：绑定裁决、原结算及当前调整 head；只执行一次。保留执行前后金额、执行依据和原交易编号。外部银行付款与退款继续使用独立凭证，裁决不代表银行已经转账。

机构能力分别为开案、披露批准、和解批准、仲裁裁决；密钥用途同样分开显式授予。查看案件不等于可查看原合同，通用平台角色不自动获得这些能力。自动处理只能使用明确的机构政策，不能让当前账单/结算预授权隐含批准仲裁或披露。

## 字段披露

使用按原件类型定义的固定字段白名单，不接受任意 JSONPath、对象扩展或用户传入的已脱敏对象。发送方从已验证的原记录构造投影，复核授权字段和摘要，独立签署新投影；接收方按同一严格 schema 拒绝额外字段。每个字段组的范围必须在批准界面完整可见，例如“账单总额”不能隐含发送各项费率。

投影不得携带原商业 JWS；JWS 可直接解码出未授权字段。R 验证的是双方对所披露事实的签署，不应宣称独立验证了没有收到的原文。仅有原件摘要也不证明该投影与原件相符；双方未确认必要投影时，案件继续等待证据，不能由单方报告完成裁决。技术鉴定材料可单独签署，但不得把它误标为双方确认的事实。

披露前再次检查当前授权、机构状态、密钥用途与案件版本。撤权阻止后续读取和新披露，但无法收回 R 已取得的明文或清除其他成员的备份。不得在界面承诺远端遗忘；保留/删除规则要结合案件 legal hold 和私有集合策略处理。

### 当前字段协议

`@kuintessence/shared/federation/disclosure` 提供 `CommercialDisclosureGrantSchema`、`CommercialDisclosureSchema` 和纯函数 `projectCommercialEvidence`。授权选择绑定案件、政策 ID/摘要、原合作域/版本、A/B/R、原记录 ID/摘要与有效期。接收机构必须与 A/B 不同；空字段、重复字段、通配符、任意路径、额外属性和错误原件类型均拒绝。

| 原件 | 可单独选择的字段 |
| --- | --- |
| 合同 | `consideration`、`unit`、`prices`、`termsText` |
| 用量 | `periodStart`、`periodEnd`、`measurements` |
| 账单 | `grossAmount`、`capReduction`、`discountAmount`、`dueAmount`、`lines` |
| 结算 | `unit`、`reservedAmount`、`chargedAmount`、`releasedAmount` |
| 调整 | `unit`、`previousChargedAmount`、`chargedAmount`、`reason`、`supportingEvidenceDigest` |
| 付款 | `unit`、`amount`、`occurredAt`、`evidenceDigest`、`reason` |

`prices`、`measurements`、`lines` 是显式的完整数组字段组，批准其中一组即披露该组内已定义的全部成员；不能把它们作为“总额”的隐含附带内容。嵌套组也使用严格原字段 schema，额外原文/签名属性拒绝。金额保持整数字符串，零额和明确的 null 不替换或推算。仅批准金额不自动带出单位；后续案件政策必须判断缺单位的证据是否足够裁决。

函数从原始类型校验后的数据提取选定字段，核对原记录、合同、机构、接收方、摘要和有效期，输出与原件脱离的确定性副本，不重新计算原 JWS 字节摘要。它的调用前提是调用方已经验证原件签名以及披露政策和批准；传入一个合法格式的 grant 或 digest 不能代替授权。接收方也必须核验签名和当前政策，不能仅调用响应 schema 就展示材料。政策层的审批、撤销与重放保护以及案件／逐条材料的持久化见下文；材料传输与接收 API 见下文，私有集合接线仍待完成。

8 项模块测试覆盖六类投影、大整数、总额/费率分离、确定性与原件不变、错误绑定、时间边界、额外/缺失/跨类型字段、嵌套泄漏与不含私有输入的错误。它们不等于真实三机构披露或 L09 已通过。

### 双签政策与当前授权校验

`@kuintessence/shared/federation/disclosure-authorization` 增加只授予读取范围的 `commercial-disclosure-policy`。双方分别签署同一政策正文，绑定原合同 ID/摘要、合作域、A/B、指定接收机构、允许的原件类型/字段、期限与随机盐。政策不授予仲裁、结算、扣款、外部转账或人员操作权限；额外资金动作字段被严格拒绝。仲裁执行权仍须另外预先约定，不能从披露政策推导。

每份 `commercial-disclosure` 将具体 grantId、案件/政策/原件引用、字段选择与实际投影值一起双签。没有独立的“签了 grant 就允许替换任意投影值”用途。接收侧同时验证政策和披露正文的四个 JWS，按当前信任中机构＋kid 查找唯一密钥，核对用途、有效期、撤销状态以及双方原始签名字节摘要相同。R 签名不能代替 A/B 业务批准；两边各签不同的合法正文也不算双签。

`verifyCommercialDisclosure` 的 context 必须由本地可信案件/原件记录加载，包含 grantId、caseId、policyId/摘要、合作域、合同版本/摘要、A/B/R 和原件类型/ID/摘要。`policyRevoked` 与 `grantRevoked` 都必须明确为 false；不可使用请求体中的未撤销声明。授权字段必须是双签政策的子集，授权期限不能超出政策，且当前时间必须处于授权窗口。接收方不能拿其他 grant 的未撤销状态验证本条披露。

签署用途分别新增 `commercial-disclosure-policy` 和 `commercial-disclosure`，已有密钥不自动扩权；完整用途目录上限同步为 51。Web 信任设置沿用明确勾选并补齐中英文名称，先前遗漏的付款签名用途名称也已补齐。数据库仅扩展既有 JSON 密钥用途的 TypeScript 类型，没有新增 SQL 结构或迁移。

发送前可以用 `assertCommercialDisclosurePolicy` 核对已验证的政策与待签投影范围；它不替调用方检查人员能力、政策/授权的当前持久状态或原件签名。读取状态与发布之间的竞态、机构状态、双方独立人员批准、原始材料真实性、重放存储和传输身份，仍必须在后续生产事务/传输入口中核验。共享验证返回的双签投影不是 R 对未披露原文的独立证明。

### 政策审批与本站撤销接口

迁移 `0176_opposite_black_tom.sql` 由 Drizzle 生成，新增 `federation_disclosure_policies` 及独立 `disclosure.approve` 能力。主 Server 已注册以下真人会话接口，路径前缀为 `/api/federation/commercial-agreements/:revisionId/disclosure-policies`；均按当前机构限定范围并返回 `Cache-Control: no-store`，机器身份不能调用。

| 方法与后缀 | 操作与权限 |
| --- | --- |
| `GET /` | `agreement.read`；分页或以 `policyId` 精确核对原批准，包含已过期／撤销历史 |
| `POST /draft` | `agreement.read`；提交 policyId、接收机构、原件类型／字段和截止时间，生成未批准正文 |
| `POST /approve` | `disclosure.approve`；签署并保存完整政策正文，同编号同文重试返回原批准 |
| `POST /:policyId/counterparty` | `disclosure.approve`；提交 `{approvalJws}`，核验对方同文签名后确认 |
| `POST /:policyId/revoke` | `disclosure.approve`；严格空对象 `{}`，永久撤销本站政策，重复撤销不重复写审计 |

能力须由机构显式授予，平台管理员和原合同批准者不自动获得；批准能力带有原合同读取能力。原合同须已有双方有效同文签名，当前组织、政策引用、双方及接收机构、有效期和独立签名用途均重新核对。合同到期不自动删除历史商业事实；此接口的政策只限定披露有效期，不授予重新执行过期合同的权限。政策可预先签署未来生效时间，但后续材料披露仍须处于其生效窗口。

原政策正文／摘要／签名不可替换；同编号异文并发只有一份批准可提交。同事务保存批准／附签／撤销及审计，审计失败整体回滚。附签和撤销锁定同一行，已撤销记录不能被附签或批准重放复活。撤销不依赖在线签名密钥或接收机构继续受信，因此密钥或对端失效时仍可停止本站授权。查询保留原批准、确认与撤销时间，确认时间表示双签已收齐，不代表政策此刻仍有效。

三种合作模式均可保存该政策，当前接口不提交链交易，不修改余额、账单或作业。A/B 各自批准同一正文并通过人工接口或后台交换附签；逐条 grant、当前许可与向 R 交付材料见下文；远端撤权传播及 A/B/R PDC 尚未实现。本站新财务批准冻结已接通（见下文）。本站 revoke 不等于对端已经获知，更不代表收回已交付明文。当前人工接口只向双方按原合同权限返回政策签名；后续 R 可核验双方政策签名，但具体材料仍须使用单独获批的投影，不能附带原商业 JWS。

7 项真实隔离 PostgreSQL／生产路由检查（74 个断言）通过：三模式独立批准与恢复、组织／能力／接收机构／用途隔离、同编号竞争、撤销竞态、审计回滚、签名／引用与数据库约束、HTTP 严格正文及机器身份拒绝。路由测试注入人员 principal，两个机构服务位于一个隔离数据库；它不是正式登录、双 Server mTLS 或三机构 PDC 验收。

### 逐条材料批准与本站撤销

Drizzle 生成迁移 `0183_blushing_sheva_callister.sql`，新增 `federation_disclosures`。一条 grant 固定案件、已双签政策、原件类型／编号／摘要、接收机构、字段及有效期；原批准正文同时包含精确投影值。不单独签署可以任意替换投影值的空白授权，也不把原商业 JWS 放进材料。升级先应用标准数据库迁移，再启动新版 Server；历史案件和政策不自动生成材料批准。

主 Server 注册真人接口 `/api/federation/commercial-agreements/:revisionId/disclosures`。全部操作要求当前机构的独立 `disclosure.approve`，机器身份、通用平台角色、开案权或合同读取权均不能替代；响应为 `Cache-Control: no-store`。

| 方法与后缀 | 行为 |
| --- | --- |
| `POST /draft` | 提交 grantId、caseId、policyId、recordType、recordId、recordDigest、fields、validUntil；从本站原件生成未批准投影，机构与政策摘要由服务端确定 |
| `POST /approve` | 提交完整 `commercial-disclosure`；重新读取原件并重算相同投影后签署保存，同编号同文返回原批准 |
| `POST /:grantId/counterparty` | 提交 `{approvalJws}`，核对对方对同一完整正文的签名后确认 |
| `POST /:grantId/revoke` | 严格空对象 `{}`，永久撤销本站这条授权；不依赖仍可用的签名密钥或对端信任 |
| `GET /` | 按当前机构／合同分页，支持 caseId 与 grantId 筛选；保留已撤销、过期和未附签历史 |

合同、用量、账单、结算、调整、付款六类材料复用开案服务的原件验签。合同只能是案件的原合同；其余材料须属于同一 taskId／attempt、双方和合同摘要，不能通过知道另一任务的记录 ID 披露材料。已有对签也须验证；用量是提供方签署的原事实，新的双方投影签名表示双方认可所披露内容，不把单方原报告冒称双方共同测量。金额不转为浮点数，数组字段组和字段边界沿用上文白名单。

草稿、批准及附签重查本地双签政策、指定接收机构、签名用途、当前有效期与撤销状态；客户端修改值、扩展字段、替换原件或政策摘要均拒绝。只有 FREEZE_PENDING、DISPUTED、EVIDENCE_WAITING 案件可新增批准；证据可以在冻结前置事实等待期间准备，但不会将案件提升为已冻结或已裁决。后续案件状态仍可查询历史及撤销授权。

政策读取持有共享行锁，和政策撤销串行；案件状态变化也不能穿过正在批准的事务。同一 grant 的并发批准、附签和单条撤销保留原文／原签名，撤销后不能通过重放恢复。保存前再次检查有效期和原件，审计失败整体回滚；审计仅记录引用、摘要和字段名，不复制字段值或签名。`confirmedAt` 只表示本站收齐双签，不能当作当前对外读取授权。

三种合作模式都只保存本站材料批准，不增加链待办，不改变钱款、预算或作业。附签支持人工导入及下述自动交换，没有自动向 R 交付、跨站撤权同步或 A/B/R PDC；后续发送器与接收器仍须核对两端当前授权，不能把本站未撤销当成对端未撤销。撤销不能收回已取得的明文。

## 每次读取的双边当前许可

## 冻结与状态转换

案件状态与账务执行、证据交付、链提交状态分别保存，避免一个“已完成”掩盖仍待执行的裁决。

| 状态 | 条件与允许操作 |
| --- | --- |
| `FREEZE_PENDING` | 本站已持久开案并停止新的受影响财务批准，等待对端确认及已签在途事务结果 |
| `DISPUTED` | 双方确认冻结边界，原记录和当前 head 固定；可补材料、和解或申请仲裁 |
| `EVIDENCE_WAITING` | 缺指定机构、必要披露授权或材料；继续冻结，不按超时自动判任何一方胜诉 |
| `DECIDED` | 满足授权及证据条件，裁决/和解原件已验证；仍未必记账 |
| `APPLICATION_WAITING` | 等待原账务依赖、必要背书或原交易 VALID；不另发新裁决绕过等待 |
| `RESOLVED` | 无资金动作的有效结案，或原执行回执已确认；保留全部原件与历史 |

冻结按任务和相关财务 head 定位，不冻结无关合作域余额，也不把科研执行自动取消。执行取消、数据撤权和停止证明继续使用原协议。付款作为已经发生的外部事实可以追加记录；若争议针对付款，新增更正必须纳入案件版本核对，不能借付款凭证修改合作额度。

原始观测、用量报告及技术更正继续追加保留，不因开案而丢弃新证据。冻结阻止受影响的新财务承诺和资金动作；新增事实使待裁决的证据/head 版本过时时，必须重新核对，不能沿用旧版本自动结案。

开案与自动账单/结算/调整存在竞争。Server 必须在原事务锁边界内检查案件；链码的每个相关写入读取同一案件/head，使并发修改触发 MVCC。已双签或已背书的事务不能靠删除队列撤销：先解析原结果，再冻结确定的最新 head；不确定则保持 `FREEZE_PENDING` 并保留占额。跨站点分区期间只能保证本站停止新批准，不能把未收到对端确认显示为全局已冻结。

### 本站开案与批准冻结

迁移 `0177_careless_bloodstrike.sql` 由 Drizzle 生成，保存原始开案正文、摘要、机构签名、原件引用和任务／attempt。主 Server 接通真人接口前缀 `/api/federation/commercial-agreements/:revisionId/disputes`：

| 方法与后缀 | 权限与行为 |
| --- | --- |
| `POST /draft` | `dispute.open`；提交 caseId、subject（recordType/recordId/recordDigest）、reason、requestedResolution，由本站已验证原件推导任务与合同绑定 |
| `POST /open` | `dispute.open`；核对完整草稿，再签署并持久开案、停止本站对相关任务的新财务批准 |

`dispute.open` 带有案件查看能力，不带有原合同读取或改账权；`agreement.approve`、`disclosure.approve` 和平台管理员角色均不隐含开案权限。机构签名须另行授予 `commercial-dispute`，完整用途目录上限为 52；旧密钥不自动增加用途。接口复用真人／活动组织校验和 no-store，自动化凭据不能调用。这里的机构签名表示当事方提出争议，不表示对方认可事实、接受仲裁或批准资金动作。

原件支持用量、账单、结算、调整和付款（以 receiptId 定位具体版本）。Server 从本站原表读取正文、核验机构签名／摘要、组织归属及合同／任务绑定，不能由请求指定另一个 taskId 冻结无关任务。原件已有对方签名时也须一致；尚未双签的本方财务原件仍可提出争议。开案消息只自动携带引用，不复制商业原件或其 JWS；理由与请求是当事方自由文本，目前仅在本机构案件入口读取，不自动向 R 发送。

开案与新财务批准使用同一 `(localSiteId, agreementRevisionId, taskId, attempt)` 数据库事务锁。账单、提供方新减免、结算、调整及取消退款在作出新承诺前检查未解决案件；机构自动批准复用同一检查，等待时不消耗政策计数或新增占额。开案不锁定原财务行，不影响其他任务或 attempt，也不停止科研执行。案例原文和审计同事务写入，同编号异文竞争只保留一个；审计失败不留下案件或冻结。

已经保存的批准仍可按原编号重放、交换旧签名、解析原链交易并完成既有账务义务。收回一个已签承诺不能靠停止后台或删除待办实现。原始用量及外部付款事实仍可追加；这些变化必须由后续双方确认过程重新确定冻结的财务 head，不能用开案时间戳推断全局边界。本站开案先保持 `FREEZE_PENDING`；直接／异步合作在后续同文双签冻结确认后才进入 `DISPUTED`，没有超时胜诉或解冻接口。已有双方签署的结算在开案后完成，本身不等于冻结确认。

本站开案路径不等待链，后续异步冻结确认通过独立待办存证（见下文）；机构收件和源方持久投递均已接通（见下文）。开案与收件入口只写 `FREEZE_PENDING`，独立双边确认入口可写 `DISPUTED`（见下文）。协调冻结的真实联合验收、和解／裁决及合法解除冻结仍是必做项。此接口不应被当成已经完成的跨机构争议处理。

12 项真实隔离 PostgreSQL／生产路由检查通过（77 个断言），覆盖五类原件、本站与对端隔离、独立权限／用途、错误绑定、重复开案、实际并发事务锁、原结算收尾、调整占额、外部付款更正、自动批准计数、异步模式减免和审计回滚。并发检查用数据库审计触发器暂停实际开案事务，确认新账单只能在其提交后读取冻结并拒绝；不是仅对纯函数模拟锁。HTTP 使用注入的人员 principal，业务夹具不等于真实登录、实际跨站链路或 Fabric 冻结验收。

### 机构收件与原始回执

私有机构 listener 新增 `POST /federation/v1/disputes`，正文为原 `commercial-dispute` JWS，Content-Type 必须为 application/jose。生产入口沿用机构 TLS 网关的证书验证与私有 Unix listener，不挂到普通 `/api` 人员路由；请求头的证书指纹只有在该隔离边界内才可信。

### 本地财务收尾核对

真人接口 `GET /api/federation/commercial-agreements/:revisionId/disputes/:caseId/financial-view` 要求当前机构的 `dispute.read`，不隐含原合同读取或财务批准权，自动化凭据不能调用。它对仍未解决的本站／收到的案件生成本地观察；不签署冻结确认、不改变案件状态，也不创建链提交。

| 字段／状态 | 含义 |
| --- | --- |
| records | 仅含原件类型、ID、摘要及收尾状态，按类型／ID 固定排序；不返回价格、金额、原文、签名或人员信息 |
| counterparty_waiting | 本站尚未取得对方同文批准 |
| application_waiting | 已有双签，但本站结算／调整／退款尚未记账 |
| ready | 该原件的本站步骤已完成；账单双签本身不表示付款或结算 |

接收站可在没有发送器时独立轮询；已保存的双方签名可以在链暂时不可达时返回原签名。原状态接口也显示原生待办摘要；双方当前具备 dispute.open 的人员可重试本站等待链确认的证明，原生重试保留两份签名与阶段。开案前提尚未完成的提案仍只由原开案机构重试。原商业待办重试独立检查 agreement.read＋dispute.open。

### 异步冻结证明的私有存证

迁移 `0181_nasty_anita_blake.sql` 由 Drizzle 生成，扩展既有商业待办允许 `record-dispute-freeze`。只在 `bilateral_attested` 开案方确认双方冻结证明时，同事务保存一条存证待办；接收方不重复排队。需求方或提供方都可以开案，正文中的合同双方角色不随之变化。直接模式不创建待办，链协调模式必须按原生收据确认流程完成，不能降级为双边确认。

商业 worker 复用原租约、proposal／transaction 检查点、MVCC 收据核对及重试机制。等待原合同存证完成后，重新检查本机构案件、已确认双方证明、原合同、签名用途和当前信任，再交给生产 Adapter。链不可达时仍保留 `DISPUTED`，存证待办独立显示 pending；已经提交但结果未知时保持同一 transactionId，不创建替代交易绕过结果。后续案件状态不因补交旧证明而回退。

新增 `RecordDisputeFreeze` 只在原 A/B 商业 PDC 保存开案原件和双签冻结证明。Adapter 和链码分别验证三份签名、案件摘要、合同、任务／attempt、双方、模式及时间；链码还核对已存私有合同。业务用途必须由当前信任配置显式允许 `commercial-dispute` 和 `commercial-dispute-freeze`。公开参数只有 domainId／caseId，正文和签名只放 transient／PDC，沿用该集合的原生组织背书策略；没有把第三机构加入原商业集合。

记录类型为 `dispute-freeze`，`GetRecordReceipt` 只对集合成员返回原摘要；同编号异文拒绝，同文重放不改写原记录。此入口只证明双方签署过这份边界，**不会**在链上冻结财务、扣款、核实争议主张或授权仲裁。`headDigest` 是双方同签的承诺摘要，链码不据此宣称已经核对链下完整账务。它不是 A/B/R 仲裁案件集合，授权披露与裁决仍待完成。

`GET .../disputes/:caseId/freeze` 在原独立 `dispute.read` 检查后新增本站 `attestation`，只返回待办 id、state、lastError、updatedAt；接收方没有本站待办时为 null，不推断远端存证状态。人工重试复用 `POST /api/federation/commercial-agreements/:revisionId/submissions/:submissionId/retry`，需当前组织的 `agreement.read` 和 `dispute.open`，不以一般合同批准权限代替开案权。只允许重置 needs_review 且无活跃租约的待办；保留原输入及未知交易检查点。

已确认旧案件不会被当前确认入口重新排队，本分支迁移不回填既有双签证明；如在升级前已经使用冻结确认，需另安排按原件核对后的历史补交，不能通过重新开案冒充历史。迁移尚未应用部署环境。

## 三种模式的执行

| 模式 | 案件与裁决执行 |
| --- | --- |
| 双边直接 | 通过受限 mTLS 交换原件和签名；本地事务执行已授权决定，不需要链 |
| 异步存证 | 与直接模式相同地完成业务，同事务保留私有存证待办；链不可达不阻塞已授权处理 |
| 链上协调 | 案件/裁决保存到独立私有集合，账务按原私有额度与唯一执行记录执行；本站投影等 VALID 后应用 |

链上协调的裁决执行使用窄入口校验原双方仲裁授权、指定 R 签名、证据完整性、结果范围和当前 head，不能复用管理员“直接设置余额”。共享既有金额守恒与占额规则；增额不足时继续等待，不能出现负可用额度。没有仲裁预授权时，只能走双方新签和解及原结算/调整入口。原价、用量与原账单保持不变，更正由追加记录表达。

不自动发行或转移联盟积分，不从直接/异步账本复制余额到链上；原合作域/epoch/单位不能更换。重复裁决、重复投递和重放使用原业务编号与检查点恢复；未确认写入先核对原结果。

## 实现落点与验收

共享协议新增争议对象、严格字段投影和签署用途；链码新增独立案件集合及业务入口，商业链码增加冻结检查与窄裁决执行入口。Server 复用现有独立能力、事务审计、签名交换、outbox 和 Adapter 恢复，不把仲裁流程塞进付款服务。数据库约束通过 Drizzle 生成。Web/CLI 从原任务或财务记录带筛选进入案件，R 使用只含获批材料的案件入口，不复用有完整合同权限的页面。

现有 `FabricEvidenceTrustSchema.domains.siteIds` 是两机构元组，继续用于原 A/B 域；仲裁域另存案件集合与 A/B/R 的明确映射，不把该元组整体放宽成任意成员数组。案件裁决进入 A/B 私有记账时核验案件集合的原记录；从客户端传入“已裁决”状态或裁剪后的回执不能替代原记录和签名检查。

必须覆盖以下真实验证后才能把 L03/L09 标记完成：

1. A/B 能查看原商业内容，R 在自身 Peer/私有存储中仅得到批准的投影，其他机构没有任何案件正文；公开区块、日志和错误不含探针原文。
2. 缺必要证据、错误机构、过期/撤销授权、错误密钥用途、额外字段或携带原 JWS 均拒绝；无授权保持争议，治理身份不能读原件或改账。
3. 正常和解、指定仲裁、冻结与结算竞争、重复执行、过时 head、额度不足，以及 R 无法替 AB 背书的等待路径。
4. 直接/异步处理不依赖链；链协调未经 VALID 不改变本站账目；断链、进程崩溃与原交易恢复不重复扣额或释放。
5. 正式机构身份的 Web/CLI 私有访问与机构切换检查；保留策略不清理活跃争议或执行未确认的原证据。

案件基础协议、PDC 验证、平台接线和用户验收是同一完整交付的必要部分；任何单项通过都不表示仲裁已交付。
