# 旧联邦数据库保留数据升级

本流程只适用于旧提交 `038aa6f` 的三机构数据库转换到整合后的 main 迁移基线 `90a4eaa`。普通 main 数据库继续使用常规迁移。一次性转换材料不适用于其他未知分支历史。

## 迁移历史

旧联邦分支保存 0000 至 0205 共 206 条迁移；main 保留自己的 0000–0078，并将联邦 schema 整合为 0079。两条历史从 0073 开始不同。直接对旧库执行 main 迁移会尝试创建已存在的联邦表；只修改迁移时间又会遗漏 main 结构。

转换必须核对完整来源历史、SQL 摘要和数据库 catalog。不能删库、清空权限或仅将旧库标记为已迁移。存在额外字段、缺失约束或其他迁移时，先在该库副本重新评估。

## 切换前准备

固定新旧提交、镜像 ID、交付清单及转换 SQL。目标使用本机取得并传入云内网的镜像，不能现场拉取或构建。备份业务库、登录库、权限状态、平台卷、配置、密钥及旧镜像映射，并在异机核对文件大小和 SHA-256。

多个数据库和卷的回退备份应在停止相关写入后取得；运行中的只读快照不能代替一致回退点。Peer 与 Orderer 保持原项目和原卷，不因平台迁移重建。

## 单站切换

1. 一次只维护一个机构。停止本站平台与权限服务写入，核对在途请求，不停止其他机构或四个 Orderer。
2. 在独立副本执行受控转换。锁定迁移日志和原表，核对固定的 206 条来源历史与原始结构；复用 main 0073–0078 的 SQL 补齐差异。
3. 将完整旧日志归档到 `drizzle.__drizzle_migrations_pre_main_038aa6f`，登记 main 的 80 条基线历史。提交前比较目标结构，并用 SHA-256 核对原有 224 张 public 表的全部原有列；权限服务表及其他非 KQ 对象保留。任何不一致整体回滚。
4. 在停写的本站库应用同一受控转换。运行新镜像的常规 main 迁移；该基线应无待执行项，后续版本只应用其新增迁移。
5. 按原依赖顺序以 `--no-build --pull never` 启动平台服务，保留原挂载、机构身份和资源限制。
6. 重新登录，确认原用户、机构、权限投影、合作协议、任务和资产可读取，再恢复写入。

来源与目标的 schema 比较须使用一致的 PostgreSQL 表达式形式；经过逻辑恢复重写的等价数组表达式应单独解释，不能通过删约束或忽略差异完成转换。

## 回退

发生新写入后不能直接换回旧镜像。先停止写入、保留故障现场，核对维护期间产生的外部业务或链交易，再按同一维护备份恢复数据库、权限、配置和镜像，避免数据库回退导致重复处理。

转换不修改 Peer 账本、通道、MSP 或链码定义。数据库备份也不包含链节点卷；Peer/PDC、Orderer 和对象数据按各自备份策略恢复。平台使用准备见[运行入口](trial-readiness.md)。
