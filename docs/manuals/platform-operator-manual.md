# Kuintessence 平台运营人员使用手册

本手册供平台运营人员、平台管理员和运营负责人使用，说明运营监控、审批协调、审计查询和事件处置。

## 1. 岗位定位

平台运营人员（Platform Operator）负责查看平台运行状态、跟进审批和异常、编写运营报告，并协调算力提供方处理用户问题。

### 1.1 权限边界

| 角色 | 可执行操作 | 默认不可执行操作 |
|---|---|---|
| 平台运营人员 | 查看运营概览、平台审计、用量计量和跨组织告警 | 修改 SSO、授权、证书、SSH、安全或基础设施配置 |
| 平台管理员 | 查看运营数据并管理平台级配置 | 未经业务组织授权批准数据或账号申请 |
| 超级管理员 | 管理全局成本、偏好和紧急管理能力 | 在无变更记录的情况下使用紧急权限 |

平台运营人员使用只读的 `operator` 角色，不继承算力提供方管理员权限；组织管理员也需单独获得平台运营授权。

## 2. 进入平台运营工作区

1. 通过统一身份认证登录。
2. 在左侧一级导航选择“平台管理”。
3. 进入“运营总览”或“平台审计”。
4. 核对页面显示的当前角色和可访问入口。

只读运营角色可访问运营总览和审计。技术配置变更由平台管理员按变更流程执行。

## 3. 运营总览

运营总览按安全与访问、算力与软件、用量与成本、治理与审计四类显示运行信息，同时列出审批待办和平台告警。

### 3.1 每日巡检

1. 查看平台服务、在线接入代理和计算健康状态。
2. 查看授权同步死信和授权差异。
3. 查看隔离运行环境严重异常或降级节点。
4. 查看软件访问、存储配额和执行账号申请。
5. 查看最近失败作业、文件传输和关键审计事件。
6. 记录需要算力提供方或系统运维人员跟进的事项。

### 3.2 数据真实性

页面提示“部分来源暂不可用”时，显示的只是成功返回的数据。请记录异常数据源，统计时将缺失部分标为未知，不按零事件或零用量处理。

“在线”表示接入代理控制通道正常；“计算就绪”才表示本地调度系统存在可运行资源。运营报告中应区分两项指标。

## 4. 审批协调

运营总览汇总待处理的访问、配额和账号申请。平台运营人员负责分流和跟踪，不替代资源所有方做业务决定。

### 4.1 软件访问申请

1. 核对申请人、组织、软件和使用目的。
2. 确认软件所有方和目标算力提供方。
3. 将申请分派给具备批准权限的责任人。
4. 跟踪批准、拒绝或补充材料状态。
5. 关闭后确认用户端可见状态与审批结果一致。

### 4.2 存储配额申请

1. 核对申请范围是平台文件空间还是集群文件根目录。
2. 查看当前用量、申请额度和有效期。
3. 由对应资源所有方批准或拒绝。
4. 生效后确认页面配额与存储限额一致。

### 4.3 执行账号申请

执行账号由目标算力提供方审批。平台运营人员重点检查是否存在长期无人处理、目标节点错误或用户组织不一致，不直接为用户创建集群账号。

## 5. 平台告警

### 5.1 授权同步死信

授权同步死信表示关系变更未能正常写入授权系统。运营人员应：

1. 记录死信数量、首次出现时间和影响功能。
2. 通知系统运维人员检查 Server、PostgreSQL 和 SpiceDB。
3. 在恢复后确认积压下降、死信已按流程处理。
4. 抽查受影响用户的访问权限是否与授权记录一致。

### 5.2 授权差异

授权差异表示观察结果与当前业务授权判断不一致。按角色、组织和资源归类，优先处理导致用户无法访问或越权访问的问题。

### 5.3 隔离运行环境告警

- 严重异常：必要条件不满足，相关能力不能进入就绪状态。
- 降级：仍可部分使用，需检查缺失的能力。

算力提供方策略只能继续收紧平台上限。任何调度系统不支持目标执行模式时，都不能回退到未经批准的账号模式。

### 5.4 接入代理离线

先判断是单节点、单站点还是全平台问题。单节点问题交由算力提供方；多个站点同时离线时，通知系统运维人员检查 Server 控制通道、网关和基础网络。

## 6. 平台审计

平台审计记录操作人、时间、目标资源、操作内容和结果。

### 6.1 查询方法

1. 选择合适的时间范围。
2. 按操作者、动作、资源类型或目标筛选。
3. 打开记录查看组织范围和执行结果。
4. 将关键记录编号关联到工单或运营事件。

### 6.2 审计判读

| 字段 | 关注点 |
|---|---|
| 操作者 | 是否为预期用户或服务主体 |
| 组织 | 是否位于操作者获授权范围 |
| 动作 | 是否与岗位和工单一致 |
| 目标 | 是否为预期资源 |
| 结果 | 成功、拒绝或失败原因是否清晰 |
| 时间 | 是否位于维护窗口或事件时间线内 |

引用或导出审计记录时，只选取报告所需内容。运营报告不得包含登录凭据、会话 Cookie、Bearer token、私钥或受限数据正文。

## 7. 用量与运营分析

平台运营人员可按组织、用户、集群和应用查看用量计量。

### 7.1 周期选择

- 原始：用于短时间故障核对和单作业追踪。
- 按小时：用于观察日内高峰。
- 按天：用于周报和月内趋势。
- 按月：用于跨月资源规划。

### 7.2 指标解释

CPU 核·小时、GPU 小时和内存 MB·小时来自作业终态记录。这些指标用于统计用量，不直接生成账单；未采集的存储和网络用量不能计入实际成本。

### 7.3 运营报告建议

运营周报至少包括：

- 平台可用状态和数据完整性说明。
- 在线接入代理、计算就绪节点及变化原因。
- 作业完成量、失败量和主要失败类型。
- 资源用量趋势及高峰队列。
- 审批处理量、超期待办和责任方。
- 重大告警、处置结果和遗留事项。

## 8. 跨团队协同

### 8.1 交给算力提供方

- 单站点接入代理离线或计算健康异常。
- 调度队列、执行账号、软件环境和集群文件根目录问题。
- 本组织数据、软件和账号审批。
- 作业进入原生调度系统后的站点执行问题。

### 8.2 交给系统运维人员

- 平台服务、Web、软件仓库、PostgreSQL、MinIO、SpiceDB、Casdoor 或网关不可用。
- 多站点控制通道同时异常。
- 授权同步积压、数据库或对象存储异常。
- 需要发布、回滚、备份恢复或证书更新。

### 8.3 交给平台管理员

- 技术角色、SSO 映射和平台级授权配置。
- 平台 Branding（名称、登录文案、Logo 和 favicon）配置。
- 隔离运行环境平台上限。
- SSH 凭据保管库、会话和录制策略。
- 数据脱敏、全局成本费率和平台偏好。

### 8.4 平台 Branding

平台管理员可在 Settings → Security 或 Operations → Security 打开“平台 Branding”，分别填写 `zh` 和 `en` 的平台名称、登录标题、副标题与欢迎语，并配置 Logo/favicon URL。保存需要平台级 `manage` 权限；平台运营人员可以查看平台配置，但不能修改。

文案按当前语言、中文文案、内置默认值的顺序取首个非空值。Logo 或 favicon 留空时使用 Web 镜像内的资源（`/branding/logo.svg`、`/branding/favicon.svg`）。图片地址只支持这两条同源路径或 HTTPS；Server 会拒绝其他本地路径，以及 `javascript:`、`data:`、`blob:`、HTTP、协议相对地址、凭据 URL 和控制字符。不要把访问令牌、内网凭据或未经审核的第三方资源写入 Branding。

Branding 读取失败时，登录页和已登录页面继续使用内置默认值。涉及数据库或应用升级时，交系统运维人员按[发布流程](system-operations-manual.md#release)执行。

## 9. 事件处置流程

### 9.1 准备与发现

从“平台管理 → 运营总览”、平台审计、用户反馈或监控发现异常后，登记事件工单。记录告警或反馈内容、发现时间及时区、受影响的组织、站点和功能、最近变更、审计编号，以及数据缺失情况。结合用户反馈和相关服务状态确认影响范围。

### 9.2 分级

| 等级 | 判定 | 确认时限与分派 |
|---|---|---|
| P0 | 全平台不可登录、核心数据错误或大范围权限错误 | 5 分钟内确认，立即通知平台管理员和系统运维负责人 |
| P1 | 主流程大范围阻断、多个站点不可用 | 15 分钟内确认，通知平台管理员和系统运维负责人 |
| P2 | 单站点或单功能受影响，有替代路径 | 1 小时内确认，分派算力提供方或系统运维 |
| P3 | 低频体验或报表问题 | 下一个工作日确认，记录复现条件并纳入改进队列 |

单位制度或服务级别协议更严格时，按其时限执行。超时后通过平台事件工单和当班值班群联系负责人，后续沟通使用同一工单编号。值班通讯录需列出各级负责人及联系方式。

### 9.3 跟踪

P0/P1/P2 事件按时间记录故障现象、影响范围、负责人、接单情况、处置动作和下次更新时间。责任方负责技术诊断与恢复，运营人员负责分派和沟通，工单附相关日志摘要。P3 事件记录改进队列编号，便于后续跟进。

### 9.4 恢复确认

1. 确认服务或站点恢复，分派方已经接单并提供验证结果。
2. 复查受影响的登录、访问权限、作业/工作流和文件传输。
3. 确认授权积压、队列和失败重试恢复正常，核对审计记录。
4. 记录恢复结果、遗留风险和后续安排。各项复查通过、记录完整且后续责任人明确后关闭事件；否则继续跟踪。

<a id="failure-handling"></a>

### 9.5 失败与停止条件

- 数据源部分不可用：保留成功返回的数据，标明不可用来源和开始时间，缺失部分不按零统计。
- 责任方未接单或恢复验证失败：按分级时限升级；P0/P1 不等待下一班，运营人员继续维护时间线。
- 权限或数据错误：暂停进一步查询和写入，仅保留排查所需信息，通知平台管理员和系统运维负责人。
- 尚未确认影响范围、审计不可用、无人接手，或主流程、权限、积压未复查时，保持事件打开。

## 10. 常见问题

### 10.1 运营总览正常，但用户仍无法提交

用户提交作业需有相应的组织权限、有效的执行账号映射、获准使用的调度队列，以及目标节点上可用的软件。进入具体作业的调度选址说明，逐项检查这些条件。

### 10.2 审计记录为空

确认时间范围和当前角色。若页面同时提示加载失败，应按数据源异常处理，不能判定为没有操作。

### 10.3 某组织用量突然下降

先检查统计周期、分组和时间窗口，再确认该组织作业是否进入终态、接入代理是否在线以及数据聚合任务是否正常。

### 10.4 只读角色看不到配置入口

只读角色无配置权限。请由平台管理员执行变更，运营人员负责提出需求、核对结果和记录影响。

<a id="handover"></a>

## 11. 交班清单

- 当前 P0/P1/P2 事件及下一责任人。
- 未处理或即将超期的审批。
- 离线、严重异常和降级节点。
- 授权同步积压和死信状态。
- 正在进行的维护窗口或版本观察。
- 需要次日复核的用量、审计或数据源异常。

关闭或交班时，记录事件编号、等级、发现与恢复时间及时区、受影响的组织和功能、分派及升级记录、验证结果、审计编号、当前结论和遗留风险。未结束的事件还需写明交班人、接手人、下一次检查时间、操作入口及所需权限。记录不得包含凭据、完整生产配置或受限数据正文。
