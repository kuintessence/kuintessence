# 旧联邦试验库保留数据升级到 main

本说明只适用于 `038aa6f` 交付的三机构试验库，目标为已合并的 main `90a4eaa`。普通 main 数据库继续使用原迁移入口，不需要转换。

## 为什么不能直接启动新镜像

旧联邦分支保存 0000–0205 共 206 条迁移；main 保留自己的 0000–0078，并将联邦 schema 整合为 0079。两条历史从 0073 开始不同。直接执行 main 迁移会尝试创建已经存在的联邦表；只修改最新迁移时间又会遗漏 main 的新增结构。

转换必须同时核对 schema 和完整迁移历史。不得删除业务库、清空权限数据或直接把旧库标记为已迁移。

## 已完成的隔离验证

2026-11-13 分别取得三站的只读逻辑快照，在本机隔离 PostgreSQL 16 副本中验证，未修改远端业务库。

| 检查 | 结果 |
| --- | --- |
| 来源历史 | 三站全部 206 条时间和 SQL 摘要与固定来源一致；前 73 条与 main 相同 |
| 结构补齐 | 复用 main 0073–0078 的 SQL，增加 5 张表、2 个字段及配套约束、索引 |
| KQ schema | 与全新执行 main 迁移后的库一致，包括列、约束、索引和枚举 |
| 业务数据 | 每站原有 224 张 public 表的行数及内容摘要不变 |
| 权限服务 | 同库的权限服务表和其他非 KQ 对象原样保留 |
| 迁移历史 | 原日志完整归档到 `drizzle.__drizzle_migrations_pre_main_038aa6f`，当前日志记录 main 的 80 条迁移 |
| 常规入口 | 转换后再次执行 main 迁移，无新增迁移或业务数据变化 |
| 转换保护 | 单独副本验证未知历史拒绝、提交前故障整笔回滚、成功后重复执行拒绝；成功路径用 SHA-256 核对原有 224 张表的全部原有列 |

副本与 main 的 schema 比较均经过 PostgreSQL 逻辑备份／恢复，避免把数组类型转换表达式的等价重写误报为结构变化。现场保护另以旧版 206 条迁移直接建库，确认三站线上 KQ catalog 与之完全一致；目标采用直接建立的 main catalog，保留同库权限服务对象。现场检查使用原始表达式，不删除约束或忽略差异。对应结构副本再次验证提交前回滚、成功转换和原表 SHA-256 核对。原始快照、身份信息、生成 SQL 与逐表结果保存在部署方私有验收目录，不进入源码仓库。

## 现场切换顺序

1. 固定新旧提交、镜像身份和可信交付清单。镜像仍在本机取得后传入云内网，目标不拉取或构建；本机空间不足时不挤占原材料和备份。
2. 每次只维护一个机构。停止该站平台和权限服务的数据库写入，核对在途请求；不停止其他机构或四个 Orderer，不启动调度器、Agent 或 R。
3. 备份业务库、登录库、权限状态、配置、密钥及旧镜像映射。备份涉及多个数据库和卷，应在停止相应写入后取得；本轮在线只读快照不能替代现场回退备份。
4. 用已在副本验证的一次性转换 SQL。事务内锁定迁移日志和原有表，检查来源历史、来源结构；补齐差异、归档原日志并登记目标历史，提交前核对目标结构及所有原有列的数据。任何不一致必须回滚，不能自动忽略未知字段或约束。
5. 执行新镜像自带的常规 main 迁移，应无待执行项。用 `--no-build --pull never` 按现有依赖顺序启动平台服务，保留原卷、身份和资源限制。
6. 真实重新登录，核对原用户、机构、授权、登录和权限投影；从实际页面检查合作与任务读取，再开展此次受影响的写操作验收。记录提交、镜像、操作对象和结果，不重复跑既有四节点故障或完整软件安装矩阵。

有新增写入后不能直接换回旧镜像。出现问题先停止写入并保存故障现场，按已核对的同一维护备份恢复数据库、权限状态、配置与镜像；恢复前核对期间是否产生外部交易，防止数据库回退导致重复处理。

## 边界

一次性转换材料只接受固定的 206 条来源历史和已核对的结构，不能作为任意旧版本升级器。旧库存在额外字段、缺失约束或其他迁移时，先在其副本重新评估，不套用三站结果。

平台升级不重建 Peer 账本、通道、机构身份或链码定义。既有 `038aa6f` 四节点证据继续关联原镜像；main UI／API 的验收另记，不能相互替代。
